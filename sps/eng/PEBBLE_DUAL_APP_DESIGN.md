# Pebble Watch Integration — Dual-App Bi-directional Design Document

## 1. Product Overview

The Pebble Watch Integration will support two separate apps installed on a user's Pebble smartwatch. This dual-app setup separates passive data displays from high-risk, interactive insulin delivery commands.

```
+-----------------------------------------------------------------+
|                         PEBBLE SMARTWATCH                       |
|                                                                 |
|  +---------------------------+     +--------------------------+  |
|  |     PebbleAAPS Watchface  |     |   PebbleAAPS Controller  |  |
|  |  -----------------------  |     |  ----------------------  |  |
|  |  • Read-only Passive Sync |     |  • Bolus Calculator      |  |
|  |  • BG, Trend, Timestamp   |     |  • Temp Target Settings  |  |
|  |  • Optimized Battery Life |     |  • Command Confirmation  |  |
|  +---------------------------+     +--------------------------+  |
+-----------------------------------------------------------------+
```

### 1.1 PebbleAAPS Watchface (Passive Sync)
* **Purpose**: A lightweight, passive watchface displaying essential real-time diabetes telemetry.
* **Telemetry**: Blood Glucose (BG), Trend Arrow direction, and Unix timestamp.
* **Constraint**: strictly read-only to preserve battery life and simplify local watchface code.

### 1.2 PebbleAAPS Controller App (Interactive Loop)
* **Purpose**: An interactive watch application that communicates bi-directionally with AAPS.
* **Capabilities**:
  * Request active boluses.
  * Set Temporary Targets.
  * Interactively compute boluses using the AAPS Bolus Calculator (inputs entered on watch, calculated on phone, confirmed on watch).
* **Constraint**: Requires user authentication/confirmation patterns to prevent accidental delivery.

## 2. Architectural Design

To support both apps simultaneously, AAPS utilizes a **Twin-UUID Routing Scheme**. PebbleKit routes broadcasts and listens to incoming watch events independently using the unique UUID registered for each app.

### 2.1 Twin-UUID Data Routing Flow

```mermaid

    subgraph AAPS Core (Phone)
        A[RxBus EventLoopUpdateGui] -->|Periodic Sync| B[PebblePlugin]
        B -->|Periodic Push via UUID 1| C[PebbleTransportImpl]
        D[PebbleDataReceiver via UUID 2] -->|Listen for Commands| B
        B -->|Calculations / Actions| E[AAPS Core Loop]
    end

    subgraph Pebble Watch
        C -->|Broadcast AppMessage| F[PebbleAAPS Watchface <br/> UUID 1]
        G[PebbleAAPS Controller <br/> UUID 2] -->|Send AppMessage Command| D
        B -->|Return Calculator Results via UUID 2| G
    end
```

## 3. Communication Protocol & Data Dictionary

### 3.1 Watchface Protocol (Uni-directional, Periodic)
* **UUID**: Custom UUID 1 (e.g. `54D3008F-E144-4712-B201-24BC515C40BA`).
* **Keys**:
  * `0` (BG): Integer in mg/dL.
  * `1` (TREND): Integer ordinal (0–9).
  * `4` (TIME): Int32 representation of unix timestamp (seconds).

### 3.2 Controller Protocol (Bi-directional, Command-Response)
* **UUID**: Custom UUID 2 (e.g. `A1B2C3D4-E5F6-7A8B-9C0D-1E2F3A4B5C6D`).
* **Protocol Keys**:
  * `20` (`KEY_CMD_TYPE`): Integer representing command requested.
  * `21` (`KEY_TRANS_ID`): Unique integer transaction identifier generated by the watch.
  * `22` (`KEY_CARBS`): Input carbs (scaled * 10 or grams).
  * `23` (`KEY_BG`): Input BG value (scaled).
  * `24` (`KEY_INSULIN_AMOUNT`): Requested bolus amount (scaled * 100).
  * `25` (`KEY_DURATION`): Temp Target duration in minutes.
  * `26` (`KEY_TEMP_TARGET_BG`): Requested temp target glucose value in mg/dL.
  * `27` (`KEY_STATUS_CODE`): Response status (0 = SUCCESS, 1 = PENDING_CONFIRMATION, 2 = ERROR).
  * `28` (`KEY_CALC_RESULT`): Bolus calculator calculated insulin suggestion (scaled * 100).

### 3.3 Command Type Enum Definitions
```kotlin
enum class PebbleCommand(val value: Int) {
    CALCULATE_BOLUS(1),
    CONFIRM_AND_DELIVER_BOLUS(2),
    SET_TEMP_TARGET(3),
    CANCEL_ACTIVE_TEMP_TARGET(4)
}
```

## 4. Safety & Handshake Verification

Any command altering pump states (boluses and temp targets) must implement a strict **handshake verification protocol** to guard against packet loss, accidental double-clicks, or stray Bluetooth frames.

### 4.1 Bolus Calculator Handshake Sequence

```
 Pebble Watch (Controller)                     AAPS App (Phone)
          |                                           |
          | ----- [1. CALCULATE_BOLUS] -------------> |
          |       (Carbs, BG, TransID)                |
          |                                           |
          |                                           | [Calculate via Core]
          |                                           |
          | <---- [2. Return SUGGESTION] ------------ |
          |       (Calculated Amount, Status, TransID)|
          |                                           |
    [User Reviews &]                                  |
    [Clicks CONFIRM]                                  |
          |                                           |
          | ----- [3. DELIVER_BOLUS] ---------------> |
          |       (Amount, Status, TransID)           |
          |                                           |
          |                                           | [Authenticate User &]
          |                                           | [Deliver Insulin]
          |                                           |
          | <---- [4. Delivery Status (Success)] ---- |
          v                                           v
```

> [!IMPORTANT]
> **Authentication Check**: The final step of delivering insulin from a watch command MUST require a user interaction check on the watch (e.g. long-press to unlock confirm button) and optional notification authorization on the phone to prevent unauthorized bolusing.

## 5. UI & Settings Configuration

In AAPS, the `PebbleFragment` settings pane will be updated to host two independent sections:

1. **Watchface Configuration**:
   * Text field for Target Watchface UUID.
   * Connection status trace logs toggle.
2. **Controller Configuration**:
   * Text field for Target Controller UUID.
   * Authentication requirement toggles (e.g., "Confirm on phone for boluses > 1.0 U").

> [!TIP]
> Both input fields will leverage the string trimming logic to prevent whitespace format validation issues.
