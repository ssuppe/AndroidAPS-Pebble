# AndroidAPS Pebble Plugin — Bi-Directional Command Extension Design Document

## 1. TL;DR
Extend the `plugins/pebble` module in AndroidAPS to process bi-directional commands (Bolus Calculator, Bolus Delivery, Temp Targets, Snooze Alarms, Cancel Bolus, eCarbs) from a Pebble Controller Watchapp via PebbleKit Android, built using strict Test-Driven Development (TDD) with visual verification checkpoints.

---

## 2. Invariants (Non-Negotiable Rules)
1. **TDD First**: Every single feature, mapper, processor, or lifecycle handler MUST be defined by failing unit tests (RED phase) before writing production code (GREEN phase).
2. **Thread Safety**: All PebbleKit transmissions and command executions MUST take place on `aapsSchedulers.io`.
3. **Explicit Logging Channel**: All log messages generated by the Pebble plugin or command processor MUST use `LTag.PEBBLE`.
4. **Safety & Constraint Guards**: Insulin boluses and temp targets initiated from the watch MUST be passed through `ConstraintsChecker.applyBolusConstraints` and `applyCarbsConstraints` before pump execution.
5. **Direct Execution**: Boluses confirmed on the watch execute directly via the pump manager (mirroring Wear OS behavior) without requiring secondary phone prompts.
6. **No Silent Failures**: If a command fails constraints or encounters errors, an error status response (`KEY_STATUS_CODE` = 2) with a descriptive message (`KEY_MESSAGE`) MUST be sent back to Pebble.

---

## 3. Assumptions & Scope
- **App UUID Scheme**: Dual-UUID setup.
  - **Watchface UUID**: `pebble_app_uuid` (default `54D3008F-E144-4712-B201-24BC515C40BA`) handles passive telemetry broadcasts.
  - **Controller UUID**: `pebble_controller_uuid` (default `A1B2C3D4-E5F6-7A8B-9C0D-1E2F3A4B5C6D`) handles bi-directional command AppMessages.
- **Handshake Verification (Wear OS Mirror)**: When `CALCULATE_BOLUS` runs, AndroidAPS stores `lastBolusWizard`. When `CONFIRM_AND_DELIVER_BOLUS` arrives with matching `KEY_TRANS_ID`, it uses `lastBolusWizard` calculation results and clears `lastBolusWizard = null`.
- **Glucose Unit Handling (Wear OS Mirror)**: Telemetry sends `UNITS` (`0` = mg/dL, `1` = mmol/L). Input `KEY_BG` from watch: if user unit is `mmol/L` and `KEY_BG` < 35, AndroidAPS automatically converts via `Constants.MMOLL_TO_MGDL`. If >= 35, it treats it as mg/dL.
- **Excluded Features**: Profile switching and pump priming/fill commands are explicitly out of scope.

## 4. Data Protocol Specification (`PebbleKeys.kt`)

### 4.1 Command Types (`PebbleCommand` Enum)
```kotlin
enum class PebbleCommand(val value: Int) {
    CALCULATE_BOLUS(1),            // Run Bolus Wizard (Carbs, optional BG, % dose)
    CONFIRM_AND_DELIVER_BOLUS(2), // Execute Bolus (Amount, Carbs, Carb time offset, TransID)
    SET_TEMP_TARGET(3),           // Set Temp Target (Manual or Preset lookup)
    CANCEL_ACTIVE_TEMP_TARGET(4), // Cancel Active Temp Target
    SNOOZE_ALARM(5),              // Mute / Snooze phone alarm
    CANCEL_ACTIVE_BOLUS(6),       // Emergency stop active bolus delivery on pump
    SET_ECARBS(7)                 // Log Extended Carbs (Carbs, duration, start offset)
}
```

### 4.2 AppMessage Protocol Keys
| Key Constant | Key Code | Type | Description |
| :--- | :--- | :--- | :--- |
| `KEY_CMD_TYPE` | `20` | `Int32` | Command requested (1..7 matching `PebbleCommand`) |
| `KEY_TRANS_ID` | `21` | `Int32` | Watch-generated transaction ID for matching handshake responses |
| `KEY_CARBS` | `22` | `Int32` | Input Carbs (grams) |
| `KEY_BG` | `23` | `Int32` | Input Glucose (mg/dL or scaled mmol/L) |
| `KEY_INSULIN_AMOUNT` | `24` | `Int32` | Insulin amount scaled * 100 (e.g. 1.50 U = `150`) |
| `KEY_DURATION` | `25` | `Int32` | Duration in minutes (or hours for eCarbs) |
| `KEY_TEMP_TARGET_BG` | `26` | `Int32` | Target Glucose in mg/dL |
| `KEY_STATUS_CODE` | `27` | `Int32` | Response Status (`0`=SUCCESS, `1`=PENDING_CONFIRMATION, `2`=ERROR) |
| `KEY_CALC_RESULT` | `28` | `Int32` | Bolus Wizard calculated insulin suggestion scaled * 100 |
| `KEY_MESSAGE` | `29` | `String` | Status / Error text string for watch display |
| `KEY_PERCENTAGE` | `30` | `Int32` | Bolus dose percentage adjustment (default: 100) |
| `KEY_CARB_TIME_OFFSET` | `31` | `Int32` | Carb delay offset in minutes (default: 0) |
| `KEY_PRESET_TYPE` | `32` | `Int32` | Preset TT Type (`0`=MANUAL, `1`=EATING_SOON, `2`=ACTIVITY, `3`=HYPO, `4`=CANCEL) |

1. Extend `TargetUuidProvider` and UI (`PebbleFragment`) to configure and store both Watchface & Controller UUIDs cleanly.
2. Extend `IPebbleTransport` and `PebbleTransportImpl` to support registering `PebbleDataReceiver` and sending ACKs/NACKs.
3. Implement `PebbleCommandProcessor` with 100% unit test coverage for all 7 commands.
4. Integrate `PebbleCommandProcessor` into `PebblePlugin` lifecycle with dynamic receiver re-registration on UUID changes.
5. Provide clean visual inspection checkpoints after each major stage.

---

## 6. Risks & Mitigations
- **Risk**: Packet corruption or double-clicking on watch causing duplicate boluses.
  - *Mitigation*: Handshake transaction verification (`KEY_TRANS_ID`) and storing transient `lastBolusWizard` state. Boluses must match recent calculation or pass safety constraints.
- **Risk**: Receiver leak or multiple active listeners when user updates settings.
  - *Mitigation*: Unregister existing `BroadcastReceiver` handlers before registering new ones during `onStop()` or preference updates.
- **Risk**: Log spamming or main thread blocking during calculation.
  - *Mitigation*: Force all processing off the main UI thread onto `aapsSchedulers.io` and tag logs under `LTag.PEBBLE`.
