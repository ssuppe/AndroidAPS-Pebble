# Pebble Plugin Bi-directional Command Extension — Implementation Plan

## Overview
This plan outlines the architecture, data protocol, and step-by-step implementation for extending the `plugins/pebble` module in AndroidAPS. The extension enables bi-directional communication between a Pebble watch app (Controller) and AndroidAPS, mirroring the Wear OS plugin implementation (`WearPlugin` and `DataHandlerMobile`).

---

## Architecture & Dual-App Scheme

```
+-----------------------------------------------------------------+
|                         PEBBLE SMARTWATCH                       |
|                                                                 |
|  +---------------------------+     +--------------------------+  |
|  |     PebbleAAPS Watchface  |     |   PebbleAAPS Controller  |  |
|  |  -----------------------  |     |  ----------------------  |  |
|  |  • Passive Telemetry Sync |     |  • Bolus Calculator      |  |
|  |  • BG, Trend, IOB, COB    |     |  • Preset & Manual TTs   |  |
|  |  • History Graph & Targets|     |  • Carb Offset & % Dose  |  |
|  |                           |     |  • Snooze Alarm & eCarbs |  |
|  +---------------------------+     +--------------------------+  |
+-----------------------------------------------------------------+
       ^                                    ^          |
       | Telemetry Push                     | Resp     | Commands
       | (Watchface UUID)                   | Payload  v (Controller UUID)
+-----------------------------------------------------------------+
|                        ANDROIDAPS MOBILE                        |
|                                                                 |
|  +--------------------------+      +--------------------------+ |
|  |       PebblePlugin       | ---> |  PebbleCommandProcessor  | |
|  |  • RxBus Event Subscriber|      |  • Bolus Calculator      | |

|  |  • Twin-UUID Management  |      |  • Constraints Checker   | |
|  +--------------------------+      +--------------------------+ |
+-----------------------------------------------------------------+
```

## Data Protocol Dictionary Specification

### Controller Commands Enum (`PebbleCommand`)
| Code | Command | Description |
| :--- | :--- | :--- |
| `1` | `CALCULATE_BOLUS` | Runs Bolus Wizard calculation with carbs, optional BG, and % dose adjustment |
| `2` | `CONFIRM_AND_DELIVER_BOLUS` | Delivers bolus with insulin amount, carbs, and carb time offset |
| `3` | `SET_TEMP_TARGET` | Sets temporary target (manual or preset lookup for Eating Soon, Activity, Hypo) |
| `4` | `CANCEL_ACTIVE_TEMP_TARGET` | Cancels current active temporary target |
| `5` | `SNOOZE_ALARM` | Mutes/snoozes active phone alarm from watch |
| `6` | `CANCEL_ACTIVE_BOLUS` | Emergency stop for active bolus delivery on pump |
| `7` | `SET_ECARBS` | Logs extended carbs (carbs over duration in hours with start offset) |

---

### Controller Command Keys (`PebbleKeys.kt`)
| Key Constant | Key Code | Type | Description |
| :--- | :--- | :--- | :--- |
| `KEY_CMD_TYPE` | `20` | `Int32` | Command Type Enum (`1`..`7` per `PebbleCommand`) |
| `KEY_TRANS_ID` | `21` | `Int32` | Transaction ID generated by Pebble watch for handshake matching |
| `KEY_CARBS` | `22` | `Int32` | Input Carbs (grams) |
| `KEY_BG` | `23` | `Int32` | Input Blood Glucose (mg/dL) |
| `KEY_INSULIN_AMOUNT` | `24` | `Int32` | Insulin amount scaled * 100 (e.g., 1.50 U -> `150`) |
| `KEY_DURATION` | `25` | `Int32` | Temp Target / eCarb Duration (minutes or hours for eCarbs) |
| `KEY_TEMP_TARGET_BG` | `26` | `Int32` | Temp Target Glucose value (mg/dL) |
| `KEY_STATUS_CODE` | `27` | `Int32` | Response Status (`0`=SUCCESS, `1`=PENDING_CONFIRMATION, `2`=ERROR) |
| `KEY_CALC_RESULT` | `28` | `Int32` | Calculated Bolus suggestion scaled * 100 |
| `KEY_MESSAGE` | `29` | `String` | Human-readable response or error description string |
| `KEY_PERCENTAGE` | `30` | `Int32` | Bolus percentage dose adjustment (e.g., `100`=100%, `80`=80%, `120`=120%, default: 100) |
| `KEY_CARB_TIME_OFFSET` | `31` | `Int32` | Carb time delay in minutes (e.g., `15` for +15 min delay, default: 0) |
| `KEY_PRESET_TYPE` | `32` | `Int32` | Temp Target Preset Type (`0`=MANUAL, `1`=EATING_SOON, `2`=ACTIVITY, `3`=HYPO, `4`=CANCEL) |

## Implementation Stages

## Stage 1: Protocol Keys & Twin-UUID Configuration
**Goal**: Expand protocol keys and update settings UI to support independent Watchface and Controller UUIDs.
**Success Criteria**: User can configure both Watchface UUID and Controller UUID in `PebbleFragment` with string trimming and format validation.
**Tests**: `TargetUuidProviderTest` verifying default and custom Watchface & Controller UUID retrieval.
**Status**: Not Started

### Action Items
- Add command keys `KEY_CMD_TYPE` (20) through `KEY_PRESET_TYPE` (32) to `PebbleKeys.kt`.
- Update `TargetUuidProvider.kt` to manage both `pebble_app_uuid` (Watchface) and `pebble_controller_uuid` (Controller). Default Controller UUID: `A1B2C3D4-E5F6-7A8B-9C0D-1E2F3A4B5C6D`.
- Update `pebble_fragment.xml` and `PebbleFragment.kt` to present two edit fields (Watchface UUID & Controller UUID) with save/validation logic.
- Add strings to `strings.xml`.

---

## Stage 2: PebbleKit Receiver & Transport Interface Expansion
**Goal**: Add incoming message listener capability to `IPebbleTransport` and `PebbleTransportImpl`.
**Success Criteria**: `PebbleTransportImpl` registers `PebbleDataReceiver`, handles incoming dictionaries, sends immediate ACK to Pebble, and dispatches data callbacks.
**Tests**: `PebbleTransportImplTest` verifying receiver registration and ACK response invocation.
**Status**: Not Started

### Action Items
- Extend `IPebbleTransport.kt` with:
  - `fun registerDataHandler(context: Context, uuid: UUID, onData: (transactionId: Int, dict: PebbleDictionary) -> Unit): BroadcastReceiver`
  - `fun sendAckToPebble(context: Context, transactionId: Int)`
- Implement methods in `PebbleTransportImpl.kt` wrapping `PebbleKit.registerReceivedDataHandler` and `PebbleKit.sendAckToPebble`.
- Log all transport actions using `LTag.PEBBLE`.

---

## Stage 3: Pebble Command Processor (`PebbleCommandProcessor`)
**Goal**: Create a command processor mirroring Wear OS `DataHandlerMobile` logic to execute commands safely.
**Success Criteria**: Correctly processes all 7 commands (`CALCULATE_BOLUS`, `CONFIRM_AND_DELIVER_BOLUS`, `SET_TEMP_TARGET`, `CANCEL_ACTIVE_TEMP_TARGET`, `SNOOZE_ALARM`, `CANCEL_ACTIVE_BOLUS`, `SET_ECARBS`). Applies constraints and returns structured response dictionary.
**Tests**: Unit test suite `PebbleCommandProcessorTest` covering all 7 command workflows, preset lookups, percentage scaling, carb offset, constraint checks, and error responses.
**Status**: Not Started

### Action Items
- Create `PebbleCommandProcessor.kt` in `plugins/pebble`. Inject `BolusWizardProvider`, `ConstraintsChecker`, `ActivePlugin`, `PersistenceLayer`, `ProfileFunction`, `Preferences`, `UiInteraction`, `UserEntryLogger`, `CommandQueue`, `ResourceHelper`, `DecimalFormatter`, `AAPSLogger`, `IPebbleTransport`.
- Implement `processCommand(context: Context, controllerUuid: UUID, transactionId: Int, dict: PebbleDictionary)`.
- Implement Logic for 7 command types:
  - `CALCULATE_BOLUS`: Compute bolus using `BolusWizard.doCalc(..., percentageCorrection = percentage)`. Store transient `lastCalculatedWizard` state. Respond with status `1` (`PENDING_CONFIRMATION`) and calculated suggestion (`KEY_CALC_RESULT`).
  - `CONFIRM_AND_DELIVER_BOLUS`: Extract `carbTimeOffset`. Calculate `carbsTimestamp = System.currentTimeMillis() + (carbTimeOffset * 60000)`. Validate requested amount against `lastCalculatedWizard` and max bolus constraints. Call `activePlugin.activePump.doBolus(...)`. Respond with status `0` (`SUCCESS`) or `2` (`ERROR`).
  - `SET_TEMP_TARGET`: Check `KEY_PRESET_TYPE`. Look up Eating Soon, Activity, Hypo in `Preferences` or use manual inputs. Apply target via `persistenceLayer.setTempTarget(...)`. Respond with status `0` (`SUCCESS`).
  - `CANCEL_ACTIVE_TEMP_TARGET`: Cancel active target. Respond with status `0` (`SUCCESS`).
  - `SNOOZE_ALARM`: Call `uiInteraction.stopAlarm("Muted from Pebble")`. Respond with status `0` (`SUCCESS`).
  - `CANCEL_ACTIVE_BOLUS`: Call `activePlugin.activePump.stopBolusDelivering()`. Respond with status `0` (`SUCCESS`).
  - `SET_ECARBS`: Call `doECarbs` with carbs, duration, and start offset. Respond with status `0` (`SUCCESS`).

## Stage 4: Plugin Lifecycle & Command Channel Wiring
**Goal**: Connect the command processor and twin receivers into `PebblePlugin`.
**Success Criteria**: `PebblePlugin` registers data handlers for the Controller UUID on start and unregisters them on stop or UUID preference update.
**Tests**: `PebblePluginTest` verifying receiver registration for both telemetry and controller UUIDs.
**Status**: Not Started

### Action Items
- Inject `PebbleCommandProcessor` into `PebblePlugin`.
- In `PebblePlugin.registerReceivers()`, register `dataReceiver` for Controller UUID alongside ACK/NACK receivers for Watchface UUID.
- Update preference change listener to re-register controller receivers when `pebble_controller_uuid` changes.
- Ensure all execution occurs on `aapsSchedulers.io`.
